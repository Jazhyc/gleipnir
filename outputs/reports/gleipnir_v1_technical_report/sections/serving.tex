\subsection{Self-hosting with one forward pass}
\label{sec:serving-selfhost}

The API price in Table~\ref{tab:serving} is the price per million input tokens that Sinha et al.\ report for the two base models.
Standard LLM APIs generate text, which they decode one token at a time.
Decoding is limited by how fast the GPU can read memory, so it leaves most of the arithmetic capacity of the GPU unused.
A Gleipnir monitor does not decode.
It needs only the prefill over the prompt and the two logits of Equation~\ref{eq:score} at the last position.
We therefore serve the monitor ourselves with vLLM in classification mode, which runs the prefill and returns the logits of the tokens \texttt{0} and \texttt{1}.

We measure throughput on a benchmark of 320 trajectories, sent with 128 concurrent requests and without prefix caching.
Appendix~\ref{app:serving-throughput} gives the throughput and latency after each step.
We convert throughput to cost with two hourly rates for one NVIDIA B200.
The on-demand rate of \$7.99 is what we paid at Runpod.
The committed-use rate of \$3.44 is the published on-demand rate of CoreWeave (\$8.60) with its largest published discount for committed use (60\%).
With stock vLLM in BF16 at the committed rate, self-hosting costs 3.7 times less than the API price for the 4B and 4.7 times less for the 27B.
At the on-demand rate it still costs less than the API price for both monitors.

These costs assume that the GPU is fully used.
A GPU that waits for requests costs the same per hour, so a deployment with idle time pays more for each token than Table~\ref{tab:serving} shows.
The merged BF16 checkpoints that we release run in this mode on stock vLLM, on any GPU that vLLM supports.

\subsection{Low-precision arithmetic}
\label{sec:serving-precision}

The largest gain in Table~\ref{tab:serving} comes from arithmetic at lower precision.
Stock vLLM computes in BF16, with 16 bits for each number.
The B200 has native support for floating-point formats with 8 and 4 bits (FP8 and FP4), and matrix products in these formats run faster.
Almost all of the prefill time goes to the linear projections of the model and to attention.
We run the projections around attention in FP8, the other large projections in FP4, and attention itself in an 8-bit format (MXFP8).
For each projection we quantize both the weights and the activations.
The state that the model stores between tokens and the two output logits keep their original precision.
This step lowers the cost by 1.77 times for the 4B and by 2.25 times for the 27B.

Lower precision changes the scores (Appendix~\ref{app:ablation-precision}).
Without further training, the 4B loses 0.032 pAUROC@20 on the validation set and 0.053 on the OOD suite.
This is why we train the 4B with QAD (Section~\ref{sec:training-setup}).
QAD restores the validation score, but on the OOD suite the released 4B still scores 0.034 below its own BF16 score.
The 27B loses nothing under the same arithmetic, so we release it without QAD.
This difference agrees with \citet{ouyang2025lowbit}, who report that larger models lose less from low-bit quantization.

This step has two limits.
The low-precision kernels are specific to the B200, so the serving stack runs only on this GPU; on other GPUs the BF16 checkpoints of Section~\ref{sec:serving-selfhost} apply.
The scores are also not exactly repeatable.
Two passes of the 4B over the same trajectories differ by about 0.01 per score on average, although pAUROC@20 changes by at most 0.0013.
